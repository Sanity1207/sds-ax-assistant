# SERVICE · VESSEL·ACTION 매핑 문의 자동 처리 Agent

## 1. 사용자·문제·가치
- 누구를 위한 서비스인가: 이슈대장(로컬 엑셀)에 매핑 문의를 남기는 현업 공정 엔지니어(요청자, 하루 약 10건)와, 그 문의를 처리하는 매핑 담당자(`VESSEL_ACTION`)·VESSEL 담당자(`VESSEL_MST`)·ACTION 담당자(`ACTION_MST`)
- 어떤 문제를 푸는가: 문의 1건당 약 60분(하루 약 10시간)의 수작업이 든다. 사람이 문의를 읽고, 담당을 나누고, 매핑을 조회·수정하고, 결과를 적고, 연락해야 한다. 문의의 약 40%는 ID가 빠져 있어 다시 물어봐야 하고, "애초에 세 담당자 누구의 일도 아닌 요청(정책 문의 포함)"을 사람이 일일이 구분해야 한다. "값이 이상해요" 문의는 매핑이 잘못 연결된 것인지 마스터 값 자체가 불만인지 실제 매핑 데이터를 확인해야 알 수 있다
- 지금은 어떻게 해결하나: 담당자가 수기로 읽고 분류·처리·기록·연락한다. 분류 판단이 사람마다 달라질 수 있다
- 이걸로 뭐가 좋아지나: 담당자가 Agent를 한 번 실행하면 그동안 이슈대장에 쌓인 신규 문의 행을 모두 가져와 칸 검사 → LLM 분류 → 매핑 생성/수정/삭제 또는 담당자 이관·반려·거절·확인 요청 → 이슈대장 갱신 → 메시지 발송까지 사람 개입 없이 일괄 처리한다. ID가 빠지거나 틀린 요청은 무엇이 틀렸는지, 고를 수 있는 마스터 값 목록, 값을 새로 추가하려면 어느 마스터 담당자에게 문의해야 하는지가 함께 안내되고, 정해진 규칙으로 담당자·처리상태가 일관되게 결정되며, 모든 처리가 이슈대장과 로그에 남는다.

## 2. 서비스 확장 관점
- 사내 기여: 문의 1건당 60분의 수작업을 없애 담당자 3명의 반복 업무를 줄이고, 매핑이 마스터에 실제로 있는 ID만 가리키도록 데이터 정합성을 보장한다.
- 규모: 현업 공정 엔지니어가 하루 약 10건 문의 → 매핑 문의는 Agent가 처리하고, 사람이 판단해야 하는 건은 매핑 담당자에게 확인 요청, 두 칸이 유효한 마스터 추가·변경 요청은 VESSEL·ACTION 담당자에게 이관한다
- 대체제와 차별점: 사람이 수기로 처리하면 분류가 들쭉날쭉하고 재요청 안내가 늦다. — 이 Agent는 입력 칸을 Python 규칙으로 먼저 검사하고, LLM이 문의를 분류하되, 실제 데이터 변경은 결정적 Python 도구로만 수행해 일관성과 정합성을 함께 확보한다.
- 확장 계획: 1차 버전은 SQLite·로컬 엑셀·콘솔 메시지로 외부 시스템을 대체해 구현·검증하고, 이후 (1) 사내 메신저 연동, (2) 공유 엑셀 파일로 이전, 실제 VESSEL·ACTION 마스터 및 매핑 DB 연결 순으로 교체한다. ID 대신 이름(예: "혼합탱크 1")으로 적은 문의에서 ID를 찾아 주는 기능은 1차 버전에서 제외하고 이후 확장으로 검토한다.

## 3. 사용 예상 도구·데이터
- 도구:
  - 기술 스택은 Python 3.14.8 + LangChain/LangGraph + AWS Bedrock(사용자 보유 IAM 액세스 키로 호출), openpyxl(엑셀 I/O), SQLite, pytest다. LLM은 문의 분류·ID 추출·원인 판단·고객 메시지 작성만 하고, DB 조회·변경은 아래 결정적 Python 도구로만 한다(LLM이 SQL을 직접 생성하지 않는다).
  - LLM 호출 규칙
    - 모든 호출은 temperature 0으로 고정하고, 응답은 정해진 스키마(유형·ID 필드 등)로만 받는다. 스키마로 해석되지 않는 응답은 호출 실패로 본다.
    - 모델은 우선순위 목록(환경변수 `BEDROCK_MODEL_IDS`, 쉼표로 구분, 1순위는 Claude Sonnet)으로 연결한다. 한 모델 호출이 실패하면(시간 초과, 요청 제한, 응답 스키마 오류 등) 그 모델로 최대 2회 재시도한 뒤 다음 순위 모델로 넘어간다.
    - 목록의 모든 모델이 실패하면 그 행은 처리하지 않고 배치를 즉시 멈춘다. 이때 그 행의 이슈대장·DB(`VESSEL_ACTION`)·처리 로그·메시지 로그는 전혀 바꾸지 않으므로(처리상태가 빈칸으로 남음), 다음 실행 때 그 행부터 다시 처리된다. 단, 실패한 LLM 호출의 기록은 호출 로그(`CALL_LOG`)에 남긴다. 콘솔에는 멈춘 행의 번호와 실패 사유를 출력하고 0이 아닌 종료 코드로 끝낸다. 이미 저장된 앞의 행들은 그대로 유지된다.
    - 이를 보장하기 위해 한 행에 필요한 LLM 호출(분류·원인 판단·메시지 작성)은 모두 DB 트랜잭션을 시작하기 전에 끝낸다.
    - 각 행의 처리 로그(MODEL_ID)에는 그 행의 분류 호출(Classify_Inquiry)이 실제로 응답한 모델 ID를 기록한다. 고객 식별 불가·칸 검사 반려처럼 LLM 없이 끝난 행은 비워 둔다. 한 행의 모든 LLM 호출 시도(재시도와 백업 모델 시도 포함)의 모델 ID와 성공 여부는 호출 로그(`CALL_LOG`)에 1회마다 1행씩 기록한다.
  - (Fetch_New_Issues)이슈대장 신규 행 가져오기
    파일 감시나 상주 프로세스 없이, 담당자가 명령(예: `python -m agent run`)으로 실행할 때만 동작하는 1회성 배치다.
    실행 시 이슈대장 `.xlsx`를 읽어 처리상태가 빈칸인 신규 행만 번호 순(숫자 기준)으로 가져와 한 건씩 처리하고, 모두 끝나면 종료한다.
    번호 채번: 엑셀에는 값이 고정되는 자동 증가 기능이 없으므로(`ROW()` 같은 수식은 행을 정렬·삭제하면 번호가 바뀌고, openpyxl로는 수식 결과를 읽을 수 없다) Agent가 번호를 매긴다. 실행을 시작하면 처리상태가 빈 행 중 번호 칸이 비어 있는 행에 (이슈대장의 최대 번호와 처리 로그의 최대 번호 중 큰 값 + 1)부터 차례로 번호를 매기고(처리상태가 채워진 행은 번호가 비어 있어도 그대로 두며, 최대 번호는 모든 행의 번호로 구한다. 2026-10-22 결정), 행을 처리하기 전에 이슈대장을 먼저 저장한다. 이렇게 하면 중간에 멈춰도 다음 실행에서 같은 행이 같은 번호를 유지한다.
    드롭다운 갱신: 같은 저장 단계에서 이슈대장의 숨김 시트 `마스터목록`에 `VESSEL_MST`의 VESSEL_ID 전체와 `ACTION_MST`의 ACTION_SEQ 전체를 다시 쓰고, VESSEL_ID·ACTION_SEQ 열에 이 범위를 참조하는 데이터 유효성 검사(목록, 목록에 없는 값 입력 시 중지)를 건다. 드롭다운 값은 ID만 쓴다("V001 반응기 A"처럼 이름을 붙이면 공백 때문에 여러 값으로 반려되므로). 마스터가 바뀌어도 다음 실행 때 드롭다운이 자동으로 맞춰진다.
    한 행의 처리 순서는 (1) LLM 호출을 모두 끝냄 → (2) 하나의 SQLite 트랜잭션으로 DB 변경·처리 로그·메시지 로그를 함께 커밋 → (3) 콘솔에 메시지 출력 → (4) 이슈대장에 그 행의 결과 저장이다. 그 뒤 다음 행으로 넘어간다. (2)의 커밋 도중 오류가 나면, Agent는 그 행의 DB 변경·처리 로그·메시지 로그를 모두 롤백하고, 콘솔에 행 번호와 오류 내용을 출력한 뒤 다음 행을 계속 처리한다. 롤백된 행은 이슈대장 처리상태가 빈칸으로 남으므로 다음 실행 때 다시 처리된다. 실행 끝에는 처리 건수(전체·상태별)를 콘솔에 요약 출력한다.
    중복 처리 방지: 행을 처리하기 전에 처리 로그에서 그 행의 번호를 찾는다. 번호가 이미 있으면(앞선 실행에서 DB 커밋까지 끝났지만 이슈대장 저장 전에 멈춘 경우) 다시 처리하지 않고, DB·메시지 로그를 바꾸지 않은 채 처리 로그의 결과(담당자·처리상태·처리결과·처리일시)를 이슈대장에 기입만 한다.
    파일 잠김 판단: 실행을 시작할 때 (1) 이슈대장과 같은 폴더에 Excel 잠금 파일 `~$<파일명>.xlsx`가 있거나, (2) 이슈대장을 쓰기 모드(`r+b`)로 열 수 없으면 잠긴 것으로 본다. 잠겨 있으면 아무 행도 처리하지 않고 "엑셀을 닫고 다시 실행하라"는 안내와 함께 0이 아닌 종료 코드로 끝낸다(이슈대장·DB·메시지 변경 없음).
    저장 방식: 이슈대장은 같은 폴더의 임시 파일에 먼저 저장한 뒤 원본과 교체(`os.replace`)해서, 저장 도중 실패해도 원본이 손상되지 않게 한다.
    실행 도중 저장에 실패하면(누군가 파일을 연 경우 등) 남은 행은 처리하지 않고 즉시 멈춘다. 이때 저장하지 못한 행의 번호와 처리 결과(담당자·처리상태·처리결과·처리일시)를 콘솔에 출력하고 0이 아닌 종료 코드로 끝낸다. 그 행의 결과는 처리 로그에 이미 커밋되어 있으므로, 파일을 닫고 다시 실행하면 위의 중복 처리 방지 규칙에 따라 이슈대장에 자동으로 기입된다. 이미 저장된 앞의 행들은 그대로 유지된다
  - (Check_Customer)요청자 ID 확인
    행을 처리할 때 가장 먼저 호출한다. 이슈대장 요청자 ID 칸 값이 `CUSTOMER_MST`의 CUSTOMER_ID에 있는지 확인하고, 있으면 고객 이름을 반환한다.
    요청자 ID가 비어 있거나 테이블에 없으면 문의를 분류하지 않고 '반려'(처리결과 "고객 식별 불가", 담당자 빈칸)로 끝낸다
  - (Check_Cells)VESSEL_ID·ACTION_SEQ 칸 검사
    Check_Customer 다음, 분류 전에 Python 규칙으로 호출한다. 이 검사는 문의 유형과 상관없이 모든 행에 적용한다. 문의내용이 무엇이든(마스터 등록 요청, 정책 문의 포함) 두 칸이 모두 유효한 값이 아니면 분류하지 않고 매핑 담당자 '반려'로 끝낸다. 두 칸은 드롭다운으로 마스터 값만 고르게 되어 있지만, 붙여넣기 등으로 드롭다운을 우회한 값이 들어올 수 있으므로 이 검사로 한 번 더 막는다.
    칸 검사는 할 수 있는 검사를 두 칸 모두에 하고, 찾은 문제를 모두 처리결과와 고객 메시지에 적는다(2026-10-22 결정). 칸마다 다음 중 하나로 판정한다
      - 빈 값: 칸이 비어 있다(앞뒤 공백만 있는 칸 포함). 사유는 "유효한 값 없음"이다
      - 여러 값: 앞뒤 공백을 제거한 칸 값 안에 구분자(쉼표 `,`, 슬래시 `/`, 공백·탭·줄바꿈, 세미콜론 `;`, 물결표 `~`)가 하나라도 있으면 값을 두 개 이상 쓴 것으로 본다. 사유는 "한 행에 하나의 요청만 가능"이다. 이때 구분자로 나눈 값 하나하나도 해당 마스터와 대조해(Check_Id), 마스터에 없는 값은 "등록되지 않은 ID" 사유로 함께 적는다
      - 마스터에 없는 값: 칸 값이 해당 마스터(VESSEL_ID → `VESSEL_MST`, ACTION_SEQ → `ACTION_MST`)에 없다(Check_Id). 사유는 "등록되지 않은 ID"이다
    하나라도 문제가 있으면 매핑 담당자 '반려'로 끝낸다. 처리결과는 사유마다 칸 이름을 괄호로 붙이고 "유효한 값 없음 → 한 행에 하나의 요청만 가능 → 등록되지 않은 ID" 순서로 쉼표로 잇는다. 여러 값 칸에서 나눈 값이 마스터에 없으면 칸 이름 뒤에 그 값을 적는다(예: "유효한 값 없음(ACTION_SEQ), 한 행에 하나의 요청만 가능(VESSEL_ID)", "한 행에 하나의 요청만 가능(ACTION_SEQ), 등록되지 않은 ID(VESSEL_ID, ACTION_SEQ 999)"). 고객 메시지는 아래 "유효 값 없음 안내" 형식을 따른다. 빈 값이나 마스터에 없는 값이 있는 칸만 그 칸의 마스터 목록을 안내하므로, 나눈 값이 모두 마스터에 있는 여러 값 칸에는 마스터 목록을 넣지 않는다. 여러 값이 있으면 요청을 한 행에 하나씩 나눠 다시 적으라고 안내한다
    유효 값 없음 안내(고객 메시지): (1) 칸마다 무엇이 틀렸는지(비어 있음, 여러 값과 그중 마스터에 없는 값, 마스터에 없는 값), (2) 그 칸에 쓸 수 있는 유효한 값 목록(VESSEL_ID면 `VESSEL_MST`의 ID·이름 전체, ACTION_SEQ면 `ACTION_MST`의 SEQ·설명 전체, 두 칸 모두면 두 목록 모두), (3) 목록에 없는 값을 새로 추가하고 싶으면 해당 마스터 담당자(VESSEL → VESSEL 담당자, ACTION → ACTION 담당자, `OWNER_MST`의 이름·연락처 포함)에게 직접 문의하라는 안내를 담는다. 예: "ACTION_SEQ 칸에 유효한 값이 없습니다. 유효한 값은 101 원료 투입, 102 가열, … 입니다. 새 ACTION을 추가하고 싶으시면 ACTION 담당자 오세훈(내선 1003)에게 문의해 주세요."
  - (Check_Single_Request)문의내용이 요청 하나만 담고 있는지 확인
    칸 검사를 통과해도, Classify_Inquiry가 문의내용이 두 개 이상의 매핑을 건드린다고 판단하면(예: "V001에 104 추가하고 103은 빼 주세요") 여러 값 반려와 같은 사유("한 행에 하나의 요청만 가능")로 '반려'한다. 매핑 수정의 기존 ACTION과 바꿀 ACTION은 매핑 하나를 바꾸는 것이므로 여기에 해당하지 않는다
  - (Check_Id_Match)칸 값과 문의내용 ID 일치 확인
    Check_Single_Request 다음, 유형별 처리 전에 Python 규칙으로 호출하며, 분류된 모든 유형에 적용한다. Classify_Inquiry가 문의내용에서 ID로 적힌 대상 VESSEL_ID·대상 ACTION_SEQ를 추출하면, Check_Id_Match는 그 값이 VESSEL_ID 칸·ACTION_SEQ 칸 값과 같은지 확인한다. 하나라도 다르면 매핑 담당자 '반려'(처리결과 "칸 값과 문의내용의 ID 불일치")로 끝낸다. 고객 메시지(Python 템플릿)는 어느 칸이 문의내용과 다른지 알리고, 칸과 문의내용에 정확한 ID를 같게 적어 다시 요청하라고 안내한다.
    문의내용에 ID가 적혀 있지 않으면(이름만 적었거나 ID가 없음) 비교하지 않고 통과한다. 대상 ACTION_SEQ는 생성·삭제의 대상 ACTION, 수정의 바꾸기 전 ACTION, 값 이상에서 문제 삼은 ACTION이다. 매핑 수정의 바꿀 ACTION_SEQ와 값 이상의 올바른 ACTION_SEQ는 비교 대상이 아니다
  - (Classify_Inquiry)LLM 문의 분류·ID 추출
    칸 검사를 통과한 행(두 칸 모두 유효)만 분류한다. 문의내용을 읽어 유형(매핑 생성 / 매핑 수정 / 매핑 삭제 / 값 이상 / 마스터 요청 / 담당 외 / 판단 불가)을 정한다.
    '마스터 요청'은 문의내용이 VESSEL이나 ACTION을 마스터 테이블에 추가하거나 변경해 달라는 요청(마스터 값 자체에 대한 불만, 마스터 등록과 매핑 연결을 함께 요청한 경우 포함)이다. 마스터 요청은 칸 검사를 통과한 경우(두 칸 모두 유효)에만 분류되며, Agent는 마스터를 직접 바꾸지 않고 해당 마스터 담당자(VESSEL → VESSEL 담당자, ACTION → ACTION 담당자)에게 '이관'한다. 요청 대상이 VESSEL과 ACTION 둘 다이면, Agent는 두 담당자 모두에게 이관하고 담당자 칸에 "VESSEL 담당자, ACTION 담당자"를 쉼표로 이어 적는다. 요청 대상이 VESSEL인지 ACTION인지 알 수 없으면, Agent는 이관하지 않고 매핑 담당자 '반려'(처리결과 "마스터 요청 대상 불명")로 끝내며, 고객에게 VESSEL과 ACTION 중 무엇을 추가·변경하려는지 밝혀 다시 요청하라고 안내한다(Python 템플릿). 칸이 유효하지 않으면 분류 전에 Check_Cells가 반려하고 마스터 담당자에게 직접 문의하라고 안내하므로, 이관되지 않는다.
    '값 이상'은 "값이 이상해요"처럼 무엇이 잘못됐는지(매핑인지 마스터 값인지) 매핑 데이터를 확인해야 알 수 있는 문의다. 문의내용이 "V004 이름을 바꿔 주세요", "V004 이름이 틀렸어요"처럼 마스터 값을 직접 지목하면 값 이상이 아니라 마스터 요청으로 분류한다(두 경우 모두 결과는 같다).
    매핑 수정의 바꿀 ACTION_SEQ와 값 이상(매핑 오류)의 올바른 ACTION_SEQ를 문의내용에서 추출한다.
    Agent는 이름(예: "혼합탱크 1", "원료 투입")으로 ID를 찾지 않고, 칸 대신 문의내용에서 VESSEL_ID·ACTION_SEQ를 가져오지도 않는다. 문의내용에 ID로 적힌 대상 VESSEL_ID·ACTION_SEQ는 추출하지만, 처리 대상으로 쓰지 않고 Check_Id_Match에서 칸 값과 같은지 확인하는 데만 쓴다. ID 위치는 다음과 같다.
      - VESSEL_ID 칸과 ACTION_SEQ 칸은 모든 행에서 필수다(Check_Cells)
      - ACTION_SEQ 칸은 생성·삭제에서는 대상 ACTION, 수정에서는 바꾸기 전 ACTION, 값 이상에서는 고객이 문제 삼은 연결 ACTION이다
      - 매핑 수정의 바꿀 ACTION_SEQ와 값 이상(매핑 오류)의 올바른 ACTION_SEQ는 문의내용에 ID로 적혀 있어야 한다(예: "104로 바꿔 주세요"). 없으면 정보 누락으로 반려하고 `ACTION_MST` 목록과 ACTION 담당자를 안내한다
  - (Check_Id)VESSEL_ID·ACTION_SEQ가 각 마스터(`VESSEL_MST`, `ACTION_MST`)에 존재하는지 확인
    두 칸 값은 Check_Cells에서 분류 전에 검사하고, 문의내용에서 추출한 바꿀(올바른) ACTION_SEQ는 매핑을 변경하기 전에 검사한다. 고객이 적은 ID가 마스터에 없으면 Agent는 그 ID가 들어간 매핑을 생성·수정·삭제하지 않고 '반려'하며(처리결과 "등록되지 않은 ID", 문의내용의 바꿀 ACTION_SEQ면 "등록되지 않은 ID(바꿀 ACTION_SEQ)"), 고객 메시지는 "유효 값 없음 안내" 형식을 따른다
  - (Get_Master_Guide)유효 값 없음 안내에 넣을 마스터 정보 조회

  - (Check_Mapping)값 이상 문의의 매핑 점검
    VESSEL_ID로 `VESSEL_ACTION`의 연결 ACTION 목록(ACTION 설명 포함)과 각 행의 수행 여부·수행 시각을 조회해 반환한다.
    LLM은 이 결과를 보고 원인을 판단한다:
      - 고객이 ACTION_SEQ 칸의 ACTION 대신 다른 ACTION이어야 한다고 함 → 문의내용에 ID로 적힌 올바른 ACTION_SEQ로 Update_Mapping 수정(올바른 ACTION_SEQ가 없으면 반려, 그 매핑이 이미 수행됐으면 Update_Mapping 규칙대로 확인필요)
      - 연결은 맞는데 마스터 값(VESSEL 이름, ACTION 설명) 자체가 불만 → 문제 삼은 대상의 마스터 담당자에게 '이관'(VESSEL 이름과 ACTION 설명 둘 다 불만이면 두 담당자 모두에게 이관)
      - 문제 삼은 대상을 알 수 없음 → 매핑 담당자 확인필요
  - (Create_Mapping)`VESSEL_ACTION`에 (VESSEL_ID, ACTION_SEQ) 1행 추가(EXECUTED_YN='N', EXECUTED_AT=NULL)

    Python 템플릿으로 만드는 메시지(고객 식별 불가 반려, 칸 검사 반려와 바꿀(올바른) ACTION_SEQ 누락·마스터에 없음 반려의 유효 값 없음 안내, 칸 값과 문의내용 ID 불일치 반려, 마스터 요청 대상 불명 반려)를 뺀 나머지 메시지의 본문을 LLM이 쓴다. 한 행의 LLM 메시지는 수신자 모두의 몫을 한 번의 호출로 쓴다(2026-10-22 결정).     - `ACTION_MST` (ACTION_SEQ, ACTION_DESCRIPTION) — 6건: 101 원료 투입, 102 가열, 103 교반, 104 냉각, 105 배출, 106 세정
    - `VESSEL_ACTION` (VESSEL_ID, ACTION_SEQ, EXECUTED_YN, EXECUTED_AT) — 7건: V001→101/102/103, V002→103, V003→103, V004→105, V005→106. 한 행 = ACTION 1개, 한 VESSEL에 여러 ACTION 가능, (VESSEL_ID, ACTION_SEQ)가 복합 PK라 중복 불가
      - FOREIGN KEY 제약: VESSEL_ID → `VESSEL_MST`(VESSEL_ID), ACTION_SEQ → `ACTION_MST`(ACTION_SEQ). DB가 마스터에 없는 ID를 가리키는 깨진 매핑을 허용하지 않으므로, 깨진 매핑은 없다고 가정한다. 매핑이 남아 있는 마스터 행은 삭제할 수 없다(ON DELETE RESTRICT). SQLite는 연결마다 `PRAGMA foreign_keys = ON`을 켜야 제약이 동작하므로, DB 연결 함수에서 항상 켠다
      - `EXECUTED_YN`: 해당 ACTION 수행 여부('Y' / 'N'), `EXECUTED_AT`: 수행 시각(`YYYY-MM-DD HH:MM:SS`, 미수행이면 NULL). 'Y'이면 EXECUTED_AT이 반드시 있고, 'N'이면 반드시 NULL이다
      - 시드 수행 상태: 수행됨(Y) = V001→101 `2026-10-20 09:00:00`, V001→102 `2026-10-20 10:30:00`, V002→103 `2026-10-21 14:00:00`, V004→105 `2026-10-21 16:20:00` / 미수행(N) = V001→103, V003→103, V005→106
      - 두 컬럼은 공정 측에서 기록하는 값으로, Agent는 수행 상태를 판단하거나 바꾸지 않는다. Agent가 새로 만드는 행(생성, 수정 후 행)은 항상 'N'·NULL로 시작하고, Agent가 건드리지 않은 행의 두 컬럼은 그대로 유지된다
    - `CUSTOMER_MST` (CUSTOMER_ID PK, CUSTOMER_NAME) — 5건: C001 김민수, C002 이서연, C003 박지훈, C004 최유진, C005 정하늘. 이슈대장 요청자 ID 칸 값을 CUSTOMER_ID와 맞춰 고객을 식별한다. Agent는 조회만 한다
    - `OWNER_MST` (ROLE PK, OWNER_NAME, CONTACT) — 3건(합성 값, 실제 담당자 정보로 교체 예정): 매핑 담당자 윤도현 내선 1001, VESSEL 담당자 강수진 내선 1002, ACTION 담당자 오세훈 내선 1003. 반려 메시지의 마스터 담당자 안내와 담당자 메시지 기록에 쓴다. Agent는 조회만 한다
    - `MESSAGE_LOG`(메시지 로그): MESSAGE_ID(INTEGER PK AUTOINCREMENT), ISSUE_NO(TEXT, FOREIGN KEY → `PROCESS_LOG`.ISSUE_NO, 이슈 번호), RECIPIENT_ROLE(TEXT, 수신자_구분), RECIPIENT_ID(TEXT NULL, 수신자_ID), RECIPIENT_NAME(TEXT NULL, 수신자_이름), BODY(TEXT, 본문), SENT_AT(TEXT, 발송 시각)
      - 제약: RECIPIENT_ROLE은 CHECK로 4개 값만 허용, `UNIQUE(ISSUE_NO, RECIPIENT_ROLE)`로 수신자마다 메시지 1건을 DB에서도 보장, ISSUE_NO FOREIGN KEY로 처리 로그 없이 메시지만 남는 상태를 막는다
      - 수신자_구분은 역할 이름(고객 / 매핑 담당자 / VESSEL 담당자 / ACTION 담당자)이고, 평가는 이 값으로 비교한다
      - 고객이면 수신자_ID = 요청자 ID, 수신자_이름 = `CUSTOMER_MST`의 CUSTOMER_NAME이다. "고객 식별 불가" 반려에서는 수신자_ID에 입력된 값을 그대로 적고 수신자_이름은 비워 둔다. 담당자이면 수신자_ID는 비워 두고 수신자_이름은 `OWNER_MST`의 해당 역할 OWNER_NAME을 적는다
    - `PROCESS_LOG`(처리 로그): ISSUE_NO(TEXT PK, 이슈 번호), OWNER_ROLE(TEXT, 담당자 칸 값, 빈칸은 빈 문자열), STATUS(TEXT, 처리상태, CHECK로 완료·이관·확인필요·반려·거절만 허용), RESULT(TEXT, 처리결과), PROCESSED_AT(TEXT, 처리일시), MODEL_ID(TEXT NULL, 응답 모델 ID, LLM 없이 끝난 행은 NULL). 처리상태·역할 이름 같은 값은 엑셀·평가와 같은 한글로 저장한다. 한 행의 처리 결과를 DB 변경·메시지 로그와 같은 트랜잭션으로 기록한다. 중복 처리 방지와 이슈대장 복구, 번호 채번에 쓴다
    - `CALL_LOG`(호출 로그): 도구 함수 호출과 LLM 호출을 함수 단위로, 호출 1회마다 1행씩 기록한다. LLM 호출은 재시도와 백업 모델 전환까지 포함해 시도 1회마다 1행이다. 성공한 호출뿐 아니라 실패한 호출(예외, 시간 초과, 요청 제한, 스키마 오류, 커밋 실패)도 기록한다. 컬럼은 CALL_ID(INTEGER PK AUTOINCREMENT), RUN_ID(TEXT, Agent가 실행 시작 시 만드는 실행 1회의 구분 값), ISSUE_NO(TEXT NULL, 이슈 번호, 배치 단위 호출은 NULL), CALL_TYPE(TEXT, CHECK로 'tool'·'llm'만 허용), FUNCTION_NAME(TEXT, 예: Check_Customer, Classify_Inquiry), MODEL_ID(TEXT NULL, LLM 호출이면 그 시도에 쓴 모델 ID), ATTEMPT(INTEGER NULL, LLM 호출이면 그 모델에서 몇 번째 시도인지), INPUT(TEXT, 입력 JSON), OUTPUT(TEXT NULL, 출력 JSON), SUCCESS(TEXT, CHECK로 'Y'·'N'만 허용), ERROR(TEXT NULL, 실패 사유), STARTED_AT(TEXT), ENDED_AT(TEXT)이다
      - 처리 로그가 없는 행(모든 모델 실패, 커밋 롤백)의 호출도 남겨야 하므로, ISSUE_NO에는 FOREIGN KEY를 걸지 않는다
      - 행 처리 트랜잭션과 섞이지 않도록, Agent는 한 행의 호출 기록을 메모리에 모았다가 그 행의 처리가 끝난 뒤(커밋 성공, 커밋 롤백, 모든 모델 실패 모두) 별도의 짧은 트랜잭션으로 저장한다. 그래서 행 처리가 롤백되어도 호출 기록은 남는다. 배치 단위 호출(Fetch_New_Issues 등)은 호출 직후 저장한다
      - 롤백된 행의 도구 호출(예: Create_Mapping)은 SUCCESS='Y'로 남을 수 있으므로, Agent는 커밋 자체도 하나의 도구 호출(Commit_Row)로 기록해 그 행이 실제로 반영됐는지 알 수 있게 한다
      - 기록 대상은 위 도구 목록의 함수(Fetch_New_Issues, Check_Customer, Check_Cells, Check_Single_Request, Check_Id_Match, Check_Id, Get_Master_Guide, Check_Mapping, Create_Mapping, Update_Mapping, Delete_Mapping, Send_Message, Update_Issue), Commit_Row, LLM 호출(Classify_Inquiry 문의 분류, Judge_Cause 값 이상 원인 판단, Write_Message 메시지 작성)이다
  - ID 타입: 이슈 번호, VESSEL_ID, ACTION_SEQ, CUSTOMER_ID는 DB(TEXT 컬럼)·엑셀 입출력·평가 비교 모두에서 문자열로 다룬다. 엑셀에서 숫자로 읽힌 값(예: 101)은 읽는 즉시 문자열("101")로 바꾸고, 앞뒤 공백은 제거한다
  - 테스트용 "없는" 값: 매핑이 없는 조합(V003·101, V005·105, 반려용), 마스터에 없는 ID(V999, 999, 반려용), 등록되지 않은 고객 ID(C999, 반려용)
  - Bedrock 자격 증명과 설정은 환경변수 또는 `.env`에서 읽고 코드에는 적지 않는다. 사용하는 변수는 `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`(IAM 액세스 키 방식)과 `BEDROCK_MODEL_IDS`(우선순위 순 모델 ID 목록, 쉼표로 구분)다

## 4. 서비스 정책 (가드레일 요약)
- 처리상태는 완료 / 이관 / 확인필요 / 반려 / 거절 다섯 가지다. 담당자 칸은 이관이면 해당 마스터 담당자(VESSEL 담당자 / ACTION 담당자, 대상이 둘 다면 "VESSEL 담당자, ACTION 담당자"), 고객 식별 불가 반려와 거절이면 빈칸, 나머지는 모두 '매핑 담당자'다. 이관은 두 칸이 모두 유효한 마스터 요청·마스터 값 불만에만 한다.
- 판정 순서는 고객 식별 불가(반려) → 칸 검사(빈 값·여러 값·마스터에 없는 값을 모두 검사하고 하나라도 있으면 반려) → 분류 → (매핑 요청·값 이상이면) 문의내용에 여러 요청(반려) → 칸 값과 문의내용 ID 불일치(반려, 모든 유형) → 유형별 처리다. 칸 검사까지는 문의 유형과 상관없이 모든 행에 적용한다.
- 유형별 처리: 매핑 생성·수정·삭제 → '완료'(조건에 따라 '반려', 이미 수행된 매핑의 수정·삭제는 '확인필요'), 마스터 요청 → 해당 마스터 담당자(VESSEL 담당자 / ACTION 담당자) '이관'(대상이 둘 다면 두 담당자 모두에게 이관, 대상을 알 수 없으면 매핑 담당자 '반려'), 세 담당자 누구의 일도 아닌 요청(정책 문의 포함) → 담당자 빈칸 '거절', LLM이 판단할 수 없는 문의 → '확인필요'.
- 매핑 요청·값 이상 문의는 분류 뒤에 문의내용에 여러 요청(반려) → 칸 값과 문의내용 ID 불일치(반려) → 바꿀(올바른) ACTION_SEQ 누락(반려) → 바꿀(올바른) ACTION_SEQ가 마스터에 없음(반려) → 해당 매핑 없음·이미 연결된 ACTION(반려) → 이미 수행됨(확인필요) → 실행 순서로 판정한다.
- 값 이상 문의는 VESSEL_ID로 매핑 데이터를 먼저 확인한 뒤 원인을 판단한다. 매핑 오류(고객이 ACTION_SEQ 칸의 ACTION 대신 다른 ACTION이어야 한다고 함)면 매핑 수정 '완료', 마스터 값 자체가 불만이면 해당 마스터 담당자(VESSEL 이름 → VESSEL 담당자, ACTION 설명 → ACTION 담당자) '이관', 대상을 알 수 없으면 '확인필요'로 처리한다.
- 값 이상 문의에서 매핑이 잘못됐다고 판단했지만 고객이 올바른 ACTION을 문의내용에 ID로 적지 않았으면 지어내거나 추론하지 않고 '반려'(올바른 ACTION_SEQ를 적어 다시 요청)한다.
- 요청자 ID가 비어 있거나 `CUSTOMER_MST`에 없으면 문의 유형과 상관없이 분류 전에 '반려'(처리결과 "고객 식별 불가", 담당자 빈칸)하고, 고객에게 등록된 고객 ID로 다시 요청하라고 안내한다.
- 이슈대장의 VESSEL_ID·ACTION_SEQ 열은 마스터 값만 고를 수 있는 드롭다운으로 제한하고, 두 칸은 모든 문의에서 필수다. 드롭다운을 우회한 값은 Check_Cells가 막는다.
- 한 행에는 요청 하나만 받는다. VESSEL_ID나 ACTION_SEQ 칸에 구분자(쉼표·슬래시·공백 등)가 있으면 값을 두 개 이상 쓴 것으로 보고 '반려'하고, 문의내용이 두 개 이상의 매핑을 건드리는 매핑 요청·값 이상 문의도 '반려'한다. 고객에게는 요청을 한 행에 하나씩 나눠 다시 적으라고 안내한다.
- 칸이 비어 있거나 마스터에 없는 값이면(문의내용의 바꿀 ACTION_SEQ가 마스터에 없을 때 포함) '반려'하고, 고객에게 어느 칸이 유효하지 않은지, 유효한 값 목록, 새 값을 추가하려면 연락할 마스터 담당자(이름·연락처)를 안내한다. 칸에 여러 값과 유효하지 않은 값이 함께 있으면 두 사유를 처리결과와 고객 메시지에 모두 적는다.
- 이미 수행된(EXECUTED_YN='Y') 매핑은 Agent가 수정·삭제하지 않는다. 매핑 수정·삭제(값 이상 문의의 매핑 수정 포함) 대상이 수행된 행이면 DB를 바꾸지 않고 매핑 담당자 '확인필요'로 넘기며, 처리결과에 "이미 수행된 ACTION(수행 시각)"을 적어 매핑 담당자가 판단하게 한다.
- LLM 호출이 모든 모델에서 실패하면 그 행의 이슈대장·DB·처리 로그·메시지 로그를 바꾸지 않고 배치를 멈춘다(실패한 호출의 기록은 호출 로그에 남긴다). 그 행은 다음 실행 때 다시 처리된다.
- 한 행의 DB 변경·처리 로그·메시지 로그는 하나의 트랜잭션으로 함께 커밋되거나 함께 취소된다. 커밋 도중 오류가 나면 셋 다 취소하고, 그 행의 처리상태를 빈칸으로 둔 채 다음 행을 계속 처리한다(그 행은 다음 실행 때 다시 처리된다).
- 도구 호출과 LLM 호출은 성공·실패와 상관없이 호출 1회마다 호출 로그(`CALL_LOG`)에 1행씩 기록한다. 호출 로그는 행 처리가 롤백되거나 모든 모델이 실패해도 남는다. 처리 로그에 번호가 있는 행은 다시 처리하지 않는다.
- Agent가 바꾸는 데이터 테이블은 `VESSEL_ACTION` 하나뿐이다(로그 테이블 `PROCESS_LOG`·`MESSAGE_LOG`·`CALL_LOG`는 Agent가 기록한다). `VESSEL_MST`·`ACTION_MST`·`CUSTOMER_MST`·`OWNER_MST`는 조회만 하고, 마스터에 없는 VESSEL·ACTION이 들어간 매핑은 만들지 않는다(Check_Id로 먼저 막고, FOREIGN KEY 제약이 DB에서 한 번 더 막는다). 마스터 변경은 각 담당자와 시드 스크립트로만 한다.
- 변경이 없어야 하는 경로(이관, 거절, 반려, 확인필요)에서는 DB가 그대로여야 한다.
- 처리가 끝나면 처리상태와 상관없이 항상 처리일시(Agent가 그 행을 처리한 시각)를 기입하고, 처리상태가 채워진 행은 다시 처리하지 않는다.
- 메시지는 수신자마다 1건만 보낸다. 완료·반려·거절은 고객에게 1건 보낸다. 이관·확인필요는 해당 담당자와 고객에게 보낸다(보통 2건이고, 이관 대상이 VESSEL·ACTION 둘 다면 두 담당자와 고객에게 3건). 해당 담당자(이관: VESSEL/ACTION 담당자, 확인필요: 매핑 담당자)에게 처리·확인 요청을 보내고 고객에게는 "담당자에게 전달되었고 곧 연락이 갈 것"이라고 안내하고, 고객 메시지 끝에 전달한 담당자의 이름과 연락처를 Python이 붙인다. 모든 메시지에 이슈 번호와 VESSEL_ID(있으면 ACTION_SEQ도)를 포함한다.
- 메시지 본문과 처리결과 문구(예: "매핑 생성 완료", "ACTION 담당자에게 이관", "담당 업무가 아닙니다")는 의미만 맞으면 되고 정확한 문자열은 고정하지 않는다. 이관·확인필요의 처리결과 칸은 간단한 사유를 적는다(단, 이미 수행된 매핑으로 인한 확인필요는 "이미 수행된 ACTION(수행 시각)"을 반드시 적는다).
- LLM은 AWS Bedrock으로만 호출하고(1순위 Claude Sonnet, 그다음 `BEDROCK_MODEL_IDS` 순서의 백업 모델) Anthropic 직접 API는 쓰지 않는다. 실제 메신저·실제 DB는 1차 버전에서 연동하지 않는다.
- 1차 버전 범위 제외: 이슈대장 실시간 감시(파일 저장 시 자동 처리), 마스터 자동 변경, 없는 VESSEL·ACTION 신규 생성, 정책 문의 응대, 고객 직접 입력용 UI/CLI(담당자용 실행 명령은 범위 안).

## 5. 성공 기준
- 평가 세트: `eval/cases.jsonl` 35~45건(현재 44건) (케이스당 id, path(`success_criteria.json`의 경로 id), input = {요청자 ID, 문의내용, VESSEL_ID, ACTION_SEQ}, expected = {담당자, 처리상태, 메시지_수신자(목록), db_check, 필요하면 처리결과_포함·마스터_목록_안내}). 처리상태 완료·이관·확인필요·반려·거절을 모두 포함하고, 모든 처리 경로를 변형까지 포함해 구성한다
- 판정 방식: `eval/run_eval.py`가 케이스마다 (1) SQLite(마스터·매핑·처리 로그·메시지 로그)를 시드 상태로 초기화하고, (2) 그 케이스의 input으로 행 1개짜리 이슈대장 `.xlsx`를 새로 만들고(번호는 비워 두어 Agent가 채번하게 하고, 접수일시는 파일을 만드는 시각으로 채운다), (3) 실제 운영과 같은 배치 실행(`Fetch_New_Issues` 진입점, 실제 Bedrock 호출, temperature 0)을 돌린 뒤, (4) 이슈대장 결과·DB 상태·메시지 로그를 expected와 자동 비교해 케이스별 PASS/FAIL과 전체 일치율을 출력한다. 케이스마다 실제로 응답한 모델 ID도 함께 출력한다
- 반복 실행: 전체 평가 세트를 3회 실행하고, 3회 모두 합격선을 넘어야 합격이다(한 번이라도 미달이면 0이 아닌 종료 코드)
- 항목 구성과 pass 조건: 처리 경로별 기대 상태(담당자·처리상태·메시지_수신자·db_check), 공통 조건, 수동 실행(신규 행 일괄 처리) 조건, DB 스키마(FOREIGN KEY·PK) 조건은 `success_criteria.json`을 참조한다
- `tests/test_batch_run.py`와 `tests/test_db_schema.py`는 분류 정확도가 아니라 배치 동작과 DB 제약을 검증하므로, 실제 Bedrock 대신 정해진 응답을 돌려주는 가짜 LLM(fake LLM)을 사용한다
- 합격선: 3회 실행 각각에서 분류(담당자)·처리상태 100% 일치, db_check·메시지 포함 전체 일치율 90% 이상
